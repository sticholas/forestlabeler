# Architecture

## Goal

Forest Labeler should be a small but professional QGIS plugin: easy to install, easy to reason about, safe around project data, and structured so canopy-delineation logic can be tested outside the QGIS user interface where practical.

## Proposed Module Boundaries

```text
forest_labeler.py                  QGIS plugin entrypoint and lifecycle
forest_labeler_dockwidget.py       Dock widget controller
forest_labeler_dockwidget_base.ui  Qt Designer layout
forest_labeler/
  core/                            QGIS-independent or lightly coupled algorithms
  qgis_api/                         QGIS layer, geometry, raster, and CRS adapters
  tools/                            QgsMapTool implementations
  ui/                               UI coordination helpers
  config/                           Defaults, presets, validation
  tests/                            Unit tests for pure/core behavior
prototypes/                         Original scripts kept for reference during migration
```

The current plugin is still flat because it was generated by Plugin Builder. The first architectural milestone is to create the package structure above and move behavior in small, reviewable slices.

## Design Principles

- Keep the QGIS entrypoint thin.
- Separate algorithm decisions from button clicks and map canvas events.
- Treat layer names, field names, thresholds, and presets as configuration.
- Validate project state before editing data.
- Fail with clear QGIS message bar feedback instead of silent exceptions.
- Preserve user data: edits should happen in explicit transactions and report what changed.

## Core Workflow

1. User chooses or confirms input layers:
   - canopy height model raster
   - target canopy polygon layer
   - optional species point layer
2. User activates a canopy labeling map tool.
3. User clicks an approximate tree center.
4. Plugin searches for local apex and infers crown boundary.
5. Plugin validates geometry, species-point match, fields, and CRS handling.
6. Plugin writes a polygon feature with metadata to the target layer.
7. Plugin reports success, warning, or blocked action in QGIS.

## Workflow Modes

Forest Labeler should grow as a toolkit with separate workflow modes:

- Canopy crown labeling, based first on `CanopyCrownLabeler.py`.
- Training square creation, based first on `NewTrainingSquare.py`.
- Canopy proposals within squares, treated as experimental while `PolygonsWithinSquare3.py` matures.
- Apex detection, treated as experimental while `ApexDetector.py` matures.

Each mode should have its own validation contract, UI controls, and write-safety path. Shared algorithm pieces should live in `forest_labeler_core/`; QGIS-specific layer, raster, canvas, and feature-writing adapters should stay thin and explicit.

Current package boundaries:

- `forest_labeler_core/`: pure business rules and algorithm helpers that can run in ordinary Python.
- `forest_labeler_qgis/`: QGIS adapters for layers, features, rasters, map tools, edit sessions, and UI-facing side effects.

## Feedback Loop

Production workflows should record enough context for later QA and improvement:

- settings used to generate a feature
- whether the user accepted, edited, rejected, or was unsure
- common correction reasons
- project/layer context

Feedback should first drive reporting and recommendations. Automated behavior changes should come later, after enough reviewed examples exist.

## Write Safety

Production feature-writing should be planned before it is applied:

1. Validate layer and schema.
2. Build an attribute plan in pure backend code.
3. Report skipped optional fields.
4. Apply geometry and attributes through a small QGIS adapter such as `forest_labeler_qgis/feature_writer.py`.
5. Commit or roll back the edit operation as one bounded action.

This prevents console-script behavior from silently skipping fields or partially writing features.

## Testing Strategy

Pure algorithm helpers should be unit tested with ordinary Python fixtures. QGIS-dependent behavior should be tested with lightweight integration checks where possible and manually verified in QGIS until a full QGIS test runner is configured.

## Migration Rule

Prototype code should not be deleted until its behavior is either:

- ported into production modules
- covered by tests or documented manual verification
- intentionally retired in a ticket or commit message
